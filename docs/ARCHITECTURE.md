# المعمارية وقراراتها

## الفحص
المستودع فارغ عند البدء. Node متاح؛ Docker مثبت لكن محركه غير عامل. الأصول الرسمية الأربعة موجودة.

## ADR-001: تطبيق موحد بوحدات مجال
Next.js App Router + TypeScript. مكونات خادم للقراءة وخدمات خادم للتحقق من الصلاحيات وعمليات ذرية للتغييرات. لا تصل مكونات العميل إلى قاعدة البيانات. Zod للمدخلات، Radix للحوار ولوحة الأوامر، CSS tokens مكافئ لنظام مكونات قابل لإعادة الاستخدام بدل اعتماد قالب جاهز.

## ADR-002: PostgreSQL وDrizzle
Drizzle ORM بديل ناضج مسموح به في الطلب، مع مخطط PostgreSQL واحد وهجرات SQL مراجعة. إنتاج: PostgreSQL عبر pg. تطوير محلي واختبارات: PGlite (PostgreSQL داخل WASM) على القرص، عملية واحدة فقط؛ ليس بديل تشغيل إنتاجي. يمنع التشغيل الإنتاجي دون DATABASE_URL وسر مصادقة صريح. لا تفتح عمليتين على نفس مجلد PGlite.

## ADR-003: Better Auth
مكتبة المصادقة تتولى scrypt وجلسات قاعدة البيانات وملفات تعريف HttpOnly وSameSite وحماية الأصل وتحديد المعدل. التسجيل العام مغلق. provision CLI ينشئ حسابًا بكلمة مرور يحددها المشغل دون كلمة مرور افتراضية. تعطيل الحساب يفحص في مسار الجلسة وكل خدمة مصرح بها. التهيئة الأولى شرط دخول النظام. الاستعادة عبر SMTP مع منع كشف وجود البريد؛ لا روابط أو رموز في السجلات. إنتاج HTTPS إلزامي.

## ADR-004: حدود الثقة
الدور يمنح صلاحية والنطاق يقيدها والتصنيف يقيد الوصول أكثر. موارد اللجان تعاد فقط عبر مستودع مصرح؛ المورد غير المصرح يعيد 404. التحقق على الخادم مستقل عن إخفاء التنقل. الجلسات لا تخزن مصفوفة صلاحيات قديمة؛ تحمل من قاعدة البيانات عند الطلب. لا وصول عام لملفات خاصة. مخزن الملفات المستقبلي يصدر رابطًا مؤقتًا بعد التحقق.

## ADR-005: النشاط والتدقيق
النشاط موجّه للمستخدم مع نطاق لجنة أو مالك. التدقيق مستقل يحوي السابق واللاحق ومعرّف جلسة داخلي ولا يسجل الرموز وكلمات المرور. عمليات المجال تسجل التغيير والنشاط والتدقيق في معاملة واحدة. trigger يمنع تعديل/حذف التدقيق، مع صلاحيات قاعدة بيانات إنتاجية لا تسمح بتجاوز trigger. تصدير WORM خارج قاعدة البيانات مطلوب قبل اعتماد ضمان عدم العبث ضد مدير قاعدة البيانات.

## تدفق الطلب
المتصفح → جلسة Better Auth → حالة الحساب والتهيئة → سياسة صلاحيات ← تعيينات مؤرخة ← استعلام مقيد → خدمة → معاملة تغيير + نشاط + تدقيق → رد عربي.

## مخاطر وضوابط نشر
SMTP وHTTPS ونسخ احتياطي واستعادة واختبار PostgreSQL خارجي مطلوبة في بيئة النشر. PGlite لا يدعم عدة عمال. تهيئة الأدوار عبر CLI موثوق في الإصدار التأسيسي؛ واجهة محرر السياسات لاحقة. لا OAuth أو SSO قبل وجود بيانات الاعتماد والجهة الجامعية؛ يوفر Better Auth مسار التوسع. إدارة الملفات والأتمتة عقود تصميم فقط في المرحلة الأولى. التشغيل الفعلي للإنتاج يحتاج مراجعة أمنية وتشغيلية مستقلة.

المراجع: https://nextjs.org/docs/app/guides/authentication ، https://better-auth.com/docs/authentication/email-password ، https://orm.drizzle.team/docs/connect-pglite

## ADR-006: محرك العمل في المرحلة الثانية

جدول work_items مشترك مع تفاصيل منفصلة لكل نوع. access.ts يقيد الاستعلامات بالنطاق والفصل؛ engine.ts يدير الانتقالات والتعيينات والاعتماديات والمراجعات في معاملات. قفل صف الفصل قبل إعادة قراءة العنصر يمنع سباقات الانتقال ودورات الاعتماديات المتزامنة، ويقايض سرعة الكتابة داخل الفصل لصالح الاتساق. version يمنع حفظ نسخة واجهة قديمة.

queries.ts يشتق الوارد والبحث من البيانات الفعلية. التنبيه مرتبط بالعمل ويعاد فحص وصوله عند العرض والقراءة. storage.ts يوفر واجهة تخزين خاصة وتنفيذ PostgreSQL bytea ذريًا مع بيانات المرفق؛ التنزيل يمر عبر تحقق المورد الأب. تخزين الكائنات الخارجي يتطلب تطبيق واجهة الموفر وسياسة الاحتفاظ والفحص. عامل due-work مستقل ومكرر بأمان، دون منصة أتمتة. تفاصيل الحدود في WORK_ENGINE.md.

## ADR-007: الفعالية غرفة عمليات مترابطة

المرحلة الثالثة توسع work_items بنوع event وتفاصيل علائقية وتعيد استخدام الموافقات والتدقيق والتنبيهات. عناصر العمل تحمل event_id اختياريًا؛ لا يُنسخ محرك المهام. متطلبات الجاهزية بوابات قابلة للتكوين؛ النسبة مشتقة والموانع مفهومة. تقرير الفعالية مستقل عن حالة الفعالية مع مراجعة قبل الأرشفة. أدوار فريق مؤرخة لا تعادل دورًا تنظيميًا، وبيانات الحضور والميزانية والملفات المصنفة لها صلاحيات إضافية. Playbook ورشة العمل من قاعدة البيانات ويُطبق داخل معاملة واحدة. تفاصيل القرار والحدود في EVENT_ENGINE.md.
