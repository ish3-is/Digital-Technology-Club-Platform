# تقرير التسليم — ٢٨ سبتمبر ٢٠٢٦

الحالة الحالية موثقة في تقرير المرحلة الثالثة في نهاية هذا الملف. تقارير المراحل السابقة محفوظة كسجل تاريخي؛ حدودها وتوصياتها تخص وقت تسليمها، ويحل تقرير المرحلة الثالثة محل الميزات التي أصبحت منفذة.

## المرحلة صفر — مكتملة

تم فحص المجلد الفارغ وتثبيت نموذج المجال وحدوده، الأدوار ومصفوفة الصلاحيات والنطاق والملكية، دورات الحياة، ERD تأسيسي ومستهدف، عقود API، خريطة التنقل، tokens، استراتيجية الشعارات وخارطة المراحل والمخاطر.

الملفات: PRODUCT.md، ARCHITECTURE.md، DOMAIN_MODEL.md، AUTHORIZATION.md، DATABASE.md، API.md، DESIGN_SYSTEM.md، ROADMAP.md.

القرارات: تطبيق موحد بوحدات مجال؛ Next.js وTypeScript، Drizzle بديل ORM ناضج، PostgreSQL مع PGlite للتطوير فقط، Better Auth للمصادقة، Radix للحوار القابل للوصول، خط عربي محلي وCSS tokens. المراجعة: تطابق نطاق المرحلة الأولى مع مخطط الجداول، وفصل الجداول المستقبلية عن التنفيذ الحالي. لا ملفات فعلية لمالية أو نقاط أو فعاليات كاملة.

## المرحلة الأولى — منفذة ومتحقق منها محليًا

- دخول وخروج وجلسات مخزنة في PostgreSQL، تهيئة أولى، ملف شخصي، عرض وإلغاء الجلسات، تعطيل وتفعيل الحسابات عبر أداة التشغيل.
- استعادة كلمة المرور عبر Better Auth وموصل SMTP؛ مسار الرمز أحادي الاستخدام واختبار إبطال الجلسات. إرسال البريد الخارجي نفسه لم يختبر لغياب إعدادات البريد.
- أدوار وصلاحيات من قاعدة البيانات، نطاق لجنة وملكية، رفض الوصول غير المصرح في API وصفحات الإدارة واللجان. تعيينات مؤرخة وفصول أكاديمية.
- تحديث نبذة اللجنة والملف الشخصي في معاملة مع النشاط والتدقيق. حماية سجل التدقيق من UPDATE وDELETE. تنبيهات شخصية يمكن تعليمها كمقروءة.
- واجهة عربية RTL أصلية، شعارات رسمية من الملفات دون تعديلها، وضع فاتح/داكن، شريط جوال، قائمة أوامر بالكيبورد، حالات فارغة. مساحات المشرف والإدارة واجهات تأسيسية بصلاحيات فعلية.
- لا بيانات تشغيلية مختلقة. قاعدة التشغيل المحلية فارغة من المستخدمين والأعمال. حساب المتصفح الاختباري في قاعدة منفصلة وموسوم ببيانات تجريبية.

مجموعات الملفات: src/db للمخطط والاتصال والأدوار، migrations لهجرة ١٦ جدولًا، src/lib للمصادقة والسياسة والخدمات، src/app وsrc/components للواجهة والمسارات، public/brand للأصول الرسمية، scripts للهجرة والحسابات والتنظيم، tests للوحدات والتكامل والمتصفح، README للتشغيل.

## الحدود المتبقية

1. هذه ليست شهادة جاهزية إنتاجية. لم تُختبر قاعدة PostgreSQL خارجية متعددة الاتصالات أو النسخ الاحتياطي أو TLS أو البريد الفعلي في هذه البيئة.
2. أنشئ أول حساب إداري ببياناتك عبر README؛ لا توجد بيانات دخول افتراضية. أوقف خادم PGlite قبل أدوات التشغيل؛ PGlite للتطوير بعملية واحدة فقط.
3. إدارة الأدوار والحسابات والتنظيم متاحة بأدوات CLI موثوقة، وواجهة الإدارة shell فقط. محرر أدوار تفاعلي، SSO، موفر التخزين، الأتمتة والتحليلات ليست ضمن هذا التسليم.
4. قسم التحديثات يعرض آخر نشاط متاح للمستخدم؛ المقارنة الدقيقة بآخر زيارة ما زالت لاحقة. صندوق الوارد يعرض التنبيهات الفعلية، وتوحيد مهام وموافقات وطلبات ينتظر وحداتها.
5. حماية التدقيق بـ trigger لا تحمي من مالك قاعدة بيانات يملك تعطيله؛ النقل إلى مخزن تدقيق خارجي غير قابل للمحو والتحكم بصلاحيات التشغيل مطلوب قبل ضمان ضد هذا الخصم.
6. اختبارات الجوال على محاكاة عرض Edge وليست أجهزة فعلية أو مراجعة كاملة بقارئ شاشة. معظم معايير الوصول مطبقة في المكونات لكن مراجعة وصول مستقلة لم تجر.

## المرحلة التالية الموصى بها

المرحلة الثانية: وحدة العمل، بدءًا بمهمة مرتبطة بلجنة وفصل ومسؤول، ثم الطلبات والاعتماديات والقرارات وصندوق وارد موحد. اعتماد التدفق واختبار النطاق والانتقالات قبل إضافة غرفة عمليات الفعالية.

## 10. Known limitations

التحقق محلي عبر PostgreSQL المضمن PGlite؛ PostgreSQL خارجي متعدد الاتصالات وSMTP وTLS والنسخ الاحتياطي لم تُختبر في بيئة إنتاج. المرفقات PNG/JPEG/TXT بحد 5 MiB و20 ملفًا لكل عمل، محفوظة خاصة في قاعدة البيانات؛ التحقق من النوع والتوقيع لا يعادل فحص برمجيات خبيثة. عامل work:due يتطلب جدولة خارجية في الإنتاج، ولا يعمل تلقائيًا على هذا الجهاز. المعاملات تتسلسل داخل الفصل لضمان الاتساق وقد تحتاج تحسينًا مع الحجم. مراجعة الاعتماد الحالية خطوة واحدة محددة، وليست مصمم مسارات. التصفح والقوائم بلا pagination مخصص للأحجام الكبيرة. الوصول اختُبر بالمكونات ولوحة المفاتيح ومحاكاة الجوال، وليس اعتماد قارئ شاشة أو أجهزة فعلية. إدارة التنظيم والحسابات عبر CLI كما في المرحلة الأولى.

## 11. Screens / features intentionally deferred

غرفة عمليات الفعالية، التقويم التفاعلي وGantt، السحب والإفلات، Workflow Builder، التصدير، الذكاء الاصطناعي، التحليلات المتقدمة، النقاط والمالية والمعرفة الكاملة، SSO، تخزين كائنات خارجي والفحص الأمني للملفات. لا تعرض هذه الميزات كأزرار تشغيل وهمية.

## 12. Recommended Phase 3

دورة الفعاليات وغرفة العمليات: ربط الفعالية بالمهام والطلبات والاجتماعات الموجودة، قوائم جاهزية مفسرة، التسجيل والحضور، وقفل الإغلاق بالتقرير. تبدأ بعد مراجعة هذه المرحلة واعتماد نطاق المرحلة التالية؛ لم تُنفذ تلقائيًا.


# تسليم المرحلة الثالثة — محرك عمليات الفعاليات

## 1. Summary

استُكمل المشروع القائم فوق المرحلتين الأولى والثانية. الفعالية غرفة عمليات فعلية مرتبطة بالعمل واللجان والفريق والموافقات والتسجيل والحضور والأدلة والمخاطر والتقرير النهائي. لا بيانات تشغيل مختلقة ولا تنفيذ للمرحلة الرابعة.

## 2. Architecture changes

src/lib/events يفصل النموذج والوصول والأوامر والاستعلامات والتخزين والإعدادات. الفعالية نوع داخل work_items، فتستخدم محرك العمل والموافقات والنشاط والتدقيق والتنبيهات الموجود. event_id ينتقل من الاجتماع إلى القرار ثم المهمة، ومن الطلب إلى مهمته؛ الربط لا يوسع النطاق تلقائيًا. القفل والمعاملة والإصدار تحمي الاتساق؛ تفاصيل المعمارية في EVENT_ENGINE.md.

## 3. Database migrations

0003_majestic_morlun.sql تضيف ١٠ جداول: events، event_playbooks، event_roles، event_team، event_requirements، event_risks، event_participants، event_attendance، event_files، event_reports. الإجمالي ٤٣ جدولًا. تضيف event_id وtrack إلى العمل، وpurpose إلى الموافقة. الهجرات السابقة محفوظة؛ الإعدادات الافتراضية تضيف قالب ورشة وأدوار فريق دون إنشاء فعاليات أو حضور في قاعدة التشغيل.

## 4. Event lifecycle

فكرة → تخطيط → انتظار اعتماد → معتمدة → فتح التسجيل → تجهيز → جاهزة للتنفيذ → تنفيذ → تقييم → تقرير نهائي → أرشفة. يسمح بتقديم الفكرة مباشرة للاعتماد، وبدء التجهيز دون التسجيل عند عدم الحاجة إليه. اعتماد مستقل يفتح approved؛ طلب تعديل يعيد planning، والرفض يغلق cancelled مع حفظ القرار. الموانع والتجاوز المصرح موثقة، والأرشفة تتطلب تقريرًا معتمدًا إذا كان إلزاميًا.

## 5. Readiness calculation

الجاهزية = عدد المكتمل ÷ إجمالي المتطلبات × ١٠٠ مع التقريب؛ غياب المتطلبات يعطي «غير محددة». قائمة فحص قابلة للتكوين بالتصنيف والإلزامية والمالك والموعد والدليل والمرحلة. الشرح يعرض المتبقي والمتأخر والموانع. قالب الورشة ينشئ ٨ متطلبات و٣ مهام من قاعدة البيانات. المهام والطلبات غير المكتملة والمخاطر المفتوحة عالية الأثر تمنع الجاهزية والتنفيذ. التجاوز يحتاج event.override_stage وسببًا مدققًا.

## 6. Permissions

١٥ صلاحية event.*: القراءة والإنشاء والتحديث والتقديم والاعتماد والإلغاء والأرشفة والتجاوز، وإدارة الفريق والجاهزية والحضور والمشاركين والملفات، وقراءة الميزانية وإدارتها. تُقيد بالنطاق والفصل. فريق الفعالية مستقل ومؤرخ؛ لا يمنح تلقائيًا صلاحية مالية أو اعتمادًا أو عمل لجنة أخرى. بيانات المشاركين والملفات المصنفة محمية بصلاحيات إضافية.

## 7. APIs

/api/events للقائمة والإنشاء، options للخيارات، /:id لغرفة العمليات، وأوامر transition/review/requirements/readiness/team/risks/resolve-risk/participants/attendance/files/report/submit-report/edit. تنزيل محمي عبر /api/events/files/:id. work API يقبل eventId وtrack، والبحث والوارد يشملان الفعاليات. العقود التفصيلية في API.md.

## 8. UI surfaces

قائمة فعاليات مجمعة وبحث وترتيب بالمواعيد؛ غرفة عمليات بشريط مراحل وجاهزية وقرار تالٍ ومخاطر وموافقات، مع تبويبات العمل والفريق والتسجيل والحضور والإعلام والملفات والتقرير والخط الزمني. إنشاء سياقي للعمل وطلب التصميم، وعرض قرارات الاجتماع. نماذج عربية RTL على الجوال؛ حقول النماذج معطلة قبل اكتمال التهيئة لمنع فقدان إدخال المستخدم. لوحة الأوامر تدعم إنشاء الفعالية والبحث عنها وفتحها.

## 9. Tests

أضيفت ١٤ حالة وحدات وتكامل للفعاليات فوق ٣٣ سابقة، تتضمن دورة ورشة كاملة حتى التقرير والأرشفة، وإرجاع القالب كاملًا عند فشل مهمة، وعزل البيانات والملفات والبحث والوارد والفريق والمخاطر والاعتمادات وCSV والسعة والتكرار. امتد السيناريو الكامل إلى منع تغيير الميزانية والأدلة بعد تقديم التقرير. أضيف سيناريو متصفح شامل يجمع إنشاء الفعالية بالقالب، إكمال متطلبات، مهمة مرتبطة، اعتماد مستقل من الوارد، تسجيل وحضور، وطلب مرتبط يستلمه رئيس لجنة أخرى، مع فحص العرض 390 بكسل للصفحات المطلوبة.

شُغّل اختبار الفعاليات واختبارات المتصفح السابقة في مجموعتين على نفس نسخة التطبيق. لقطات الفعاليات محفوظة في .data/phase3-validation، ولقطات المراحل السابقة في test-results. روجعت صور غرفة العمليات والجاهزية والحضور بصريًا. أُصلح فقدان إدخال نموذج الاعتماد أثناء التهيئة الأولية، وتحقق الاختبار النهائي من حفظ القرار فعليًا.

## 10. Security validation

رفضت الاختبارات قراءة وتعديل فعالية خارج النطاق، وإضافة مستخدم معطل أو تمثيل لجنة غير مطابقة، وتصعيد العضو إلى إدارة الفريق، وقراءة المشاركين أو الميزانية أو ملف مصنف دون الإذن الإضافي، والانتقال غير الصالح والتجاوز دون إذن وسبب، والاعتماد غير المخول أو بالنسخة القديمة. تحقق منع كشف الفعالية عبر البحث والوارد، وانتهاء صلاحية الفريق، وربط القرار والمهمة، وعدم كشف غرفة الفعالية للجهة المستلمة لمجرد ورود طلب إليها. يظل التحقق الأمني مجموعة حالات مثبتة، لا ضمانًا مطلقًا بانعدام الثغرات.

## 11. Known limitations

التحقق محلي على PGlite وEdge بمحاكاة الجوال؛ PostgreSQL خارجي متعدد الاتصالات وTLS وSMTP والنسخ الاحتياطي وقارئ الشاشة والأجهزة الفعلية لم تعتمد إنتاجيًا. القوالب وأدوار الفريق تُضبط في قاعدة البيانات بواسطة مشغل موثوق، دون محرر إعدادات عام. التسجيل الخارجي رابط فقط دون مزامنة، وCSV حتى ٥٠٠ صف بمعاملة واحدة. السعة تحسب كل السجلات بما فيها الملغاة. الميزانية حقول مدخلة بالهللات وليست دفتر مصروفات؛ تتجمد مع التقرير المقدم أو المعتمد. الملفات PNG/JPEG/TXT حتى ٥ MiB و١٠٠ ملف للفعالية؛ لا مضاد فيروسات أو تخزين كائنات خارجي. القوائم والخط الزمني ليستا نظام أرشفة ضخمًا؛ يلزم pagination وتحسين الاستعلامات عند زيادة الحجم. سياسة الاحتفاظ ببيانات المشاركين وإجراءات النشر المؤسسي خارج هذا التسليم المحلي.

## 12. Deferred items

QR scanning وتوزيع الرموز، تقويم تفاعلي وGantt، إدارة إعلام مستقلة، شهادات آلية، مصروفات ومدفوعات كاملة، مزامنة منصات التسجيل، Workflow Builder، التصدير وAI والتحليلات المتقدمة والمعرفة المؤسسية الكاملة. البيانات مهيأة لتوسعة QR والمصروفات دون تقديم وظائف وهمية.

## 13. Recommended Phase 4

الحوكمة والأدلة: سياسات تصنيف واحتفاظ، تخزين خاص قابل للتوسع وفحص ملفات، تقارير ومراجعات مؤسسية ودفتر مصروفات مرتبط بالفعالية، مع فصل الصلاحيات المالية واختبار الاستعادة والتشغيل الإنتاجي. لا تبدأ تلقائيًا؛ التنفيذ متوقف للمراجعة بعد هذه المرحلة.

## 14. Phase 4 — Governance, Evidence & Institutional Reporting (منفذة)

استُكملت المرحلة الرابعة فوق المراحل 1-3 الموثقة أعلاه. واجهات الحوكمة صادرة من نفس محرك العمل والموافقات والدليل؛ لا وحدات مشياة. التقرير التالي يوثق ما فُتح وما فُحَص وما أُبْقي على حدوده.

### 14.1. Surfaces منفذة

- `/governance` — لوحة الحوكمة والأدلة: نبض (مهام، إكمال في الموعد، حضور، تقارير معتمدة)، مؤشرات مع تفسير الوصول لكل قياس، صحة اللجان، تنبيهات مشتقة، ومراجعات/إجراءات صندوق الوارد. التبويبات: الأهداف، المبادرات، المؤشرات، خزنة الأدلة، التقارير، مع نماذج إنشاء وتعديل وإرفاق أدلة وربطها بالقياسات، إكمال المراجعة، الاعتماد المنفصل، الأرشفة، وتجميد المحتوى بعد الاعتماد. خط زمني للأحداث وسبل الوصول لكل مورد.
- `/governance/search` — بحث حرفي في عناوين الأهداف والمبادرات والمؤشرات والأدلة والتقارير ضمن النطاق، مع أوامر بحث من لوحة Ctrl+K.
- `/governance/inbox` — صندوق الوارد المؤسسي: مراجعات تقارير مسندة، طلبات تعديل من صاحب التقرير، وبنود اعتماد بعد اكتمال توصيات المراجعين، مع تفاصيل السبب والمصدر لكل إجراء.
- `/governance/executive` — center القيادة: صورة واحدة للنادي الكامل من الأهداف للمؤشرات والتقارير والقرارات، للفريق القيادي، مع تفسير قابل للنقر لكل نسبة.
- Supervisor brief — المسار `/supervisor/brief` يعرض مراجعات التقارير المسندة إليه وإجراءات الاعتماد داخل نطاقه، منفصل عن الوارد العام. حارس الصفحة الحالي يتطلب `report.review` على نطاق النادي، كما في مسار provisioning للمشرف؛ المنح المقيدة بلجنة وحدها لا تفتح هذه الصفحة.

### 14.2. APIs منفذة

`/api/governance`: GET للقوائم والخيارات واللقطة الزمنية والبحث والوارد والتفاصيل؛ POST لأوامر الإنشاء والتعديل والقياس والربط والتحقق والمراجعة والاعتماد والأرشفة. تنزيل الأدلة المحمية عبر `/api/governance/evidence/:id/download` مع Content-Disposition مشفرة وnosniff وCSP. كل رد `private, no-store`. حد JSON هو 64000 بايت والملف 5 MiB مع هامش multipart. التحقق من الأصل على كل POST. العقود الفعلية وفصل المراجعة عن الاعتماد موثقة في `docs/API.md`.

### 14.3. Tests منفذة

`tests/governance.test.ts` — ٨ سيناريوهات: عزل الأهداف والمبادرات والمؤشرات باللجنة والفصل، رفض المنح المنتهية والفصول المغلقة، ذرية القياس وترتيب القيم المؤرخة، فصل عرض الأدلة عن التحقق مع إثبات صاحب التحقق ومنع التعديل بعد التحقق، حماية الملفات المصنفة ومنع مراجعات URLs وfileId عشوائية، دورة المراجعة المستقلة ثم الاعتماد المنفصل مع تجميد المحتوى، إرجاع changes_requested لصاحب التقرير مع الاحتفاظ بسجل المراجعة، واستعادة النطاق عند فشل التدقيق. يغطي الحالات المثبتة وليس ضمان انعدام الثغرات.

`tests/e2e/governance.spec.ts` — ٨ سيناريوهات فعلية في Edge: لوحة الحوكمة والتبويبات ومطابقة النسب مع API وفحص عرض جوال أساسي؛ البحث وعزل اللجنة والنتائج الفارغة؛ الوارد مع مراجعة مسندة ورابطها؛ مركز القيادة والمراجعة الأسبوعية؛ `/supervisor/brief` للمشرف ومنع العضو؛ طلب تعديل وإعادة تقديم وتوصية مراجعة ثم اعتماد مستقل؛ عرض الأدلة مع رفض التحقق غير المخول والتحقق المستقل ومنع تعديل الدليل المراجع؛ وCtrl+K وصولًا إلى السجل. تُفحص الحالات وقرارات الصلاحية وسجل التدقيق بعد الأوامر، وليس ظهور الأزرار فقط.

`npm run test:e2e` يجهز قاعدة PGlite جديدة ومعزولة، وينفذ الترحيلات و`scripts/seed-work-e2e.ts` ثم يشغل التطبيق تلقائيًا على `localhost:3001`، دون تشغيل يدوي. فحص الجاهزية يستهدف `[::1]:3001/login` لتجنب تعارض مستمع IPv4 على الجهاز. يستخدم التمهيد نوع التقرير التجريبي الموجود ومشرفًا مستقلًا عن رئيس اللجنة؛ لا API إنتاج إضافية لتهيئة الاختبارات.

### 14.5. حدود المرحلة الرابعة المتبقية

1. تصنيف الاحتفاظ وسياسات الاحتفاظ بالأدلة ليست منظمة بعد؛ التصنيف الأرباعي (علني/داخلي/مقيد/سري) موجود لكن سياسات الاحتفاظ والسحب ليست كذلك.
2. دفتر المصروفات والمالية المرتبطة بالفعاليات غير منفذ؛ المؤشرات تحسب من بيانات العمل والأدلة الموجودة.
3. تخزين الأدلة خاص وقابل للتوسع داخل PostgreSQL؛ التخزين الخارجي وفحص الملفات وتخزين كائنات خارجي مؤجل.
4. Pagination للقوائم الكبيرة مؤجلة؛ الحالية مناسبة للأحجام المتوقعة.
5. المراجعات تعتمد على مفوضين مسندين من أصحاب الموارد؛ لا مسار مستقل للمفوضات متعددة المستويات.
6. التقارير تدعم موادًا فردية فقط ولا تقارير متراكمة أو مقارنة فصول متعددة تلقائيًا.
7. لا توجد لوحة تحليلات متقدمة أو مراجعة وصول بقارئ شاشة مستقلة.

### 14.6. ما لم يُفسَّر كفعل

- لا توجد ترتيبات أو لوحات قيادة تجمعه Teams أو أي جهة خارجية.
- النسب والمؤشرات كلها من صيغ مُسجلة مع بسط ومقام وشرح؛ لا رقم بدون مصدر.
- صندوق الوارد مشتق من حالة التقارير والمراجعات الفعلية، وليس إشعارات عامة أو روبوت مؤشرات.
- Supervisor brief هو إجراء حقيقي على نطاق المشرف، ولا يصنف الأفراد أو الفرق.

### 14.7. التوصية

توقف التنفيذ للمراجعة. المرحلة الخامسة (الأتمتة) توصية فقط ولا تبدأ تلقائيًا.
